# Муха идёт по маршруту (NeuroMechFly v2 / FlyGym 2.1)

Учебный проект: физическая модель тела дрозофилы (NeuroMechFly v2, библиотека
[FlyGym](https://neuromechfly.org)) проходит по плоской арене маршрут из `route.yaml`.
Результат: видео, траектория в CSV и её график.

## Запуск

Нужен только Docker Desktop. Из папки проекта:

```bash
docker compose run --rm sim
```

Первый запуск сам соберёт образ (несколько минут). Пересобрать вручную: `docker compose build`.
Симуляция маршрута из примера (11.3 с) занимает около 3 минут: в Docker Desktop
с 8 CPU одна секунда модели считается примерно 15 секунд.

## Результаты (`./output`)

| Файл | Что внутри |
|---|---|
| `route.mp4` | видео с камеры, которая следует за мухой и смотрит сверху (0.5× скорость, 25 fps, 640×480) |
| `trajectory.csv` | `time_s, x_mm, y_mm, heading_deg, step, action`, каждые 10 мс |
| `trajectory.png` | траектория сверху, цвет = шаг маршрута, стрелки = направление мухи раз в секунду |
| `run.log` | ход симуляции и сводка по шагам: сколько муха прошла и на сколько градусов повернула |

Оси везде одинаковые: x вправо, y вверх. `heading_deg` = 0° значит муха смотрит вдоль +x,
положительный угол = против часовой стрелки. Поворот налево увеличивает угол.

## Как менять маршрут

`route.yaml` — список шагов, выполняются сверху вниз:

```yaml
- {action: forward, duration_s: 3.5, strength: 1.0}
- {action: left,    duration_s: 3.0, strength: 0.1}   # плавный поворот
- {action: right,   duration_s: 0.3, strength: 0.7}   # резкий поворот
- {action: stop,    duration_s: 2.0}                  # strength можно не писать
```

- `forward`: `strength` = амплитуда шага (1.0 = обычная ходьба, около 14 мм/с).
- `left` / `right`: `strength` = резкость поворота. Внешняя сторона шагает с амплитудой 1.0,
  внутренняя с амплитудой `1 − 2·strength`: 0 = прямо, 0.5 = внутренние ноги стоят,
  1.0 = внутренние ноги шагают назад (разворот почти на месте).
- `stop`: обе стороны 0, муха останавливается.

Папка проекта примонтирована в контейнер, поэтому после правки `route.yaml` или
`run_route.py` пересобирать образ не нужно. Другой файл маршрута:
`docker compose run --rm sim python run_route.py my_route.yaml`.

Скорость поворота на наших прогонах (примерно, зависит от предыдущего шага):

| strength | скорость поворота |
|---|---|
| 0.1 | ~30°/с, плавная дуга |
| 0.3 | ~90–100°/с |
| 0.7 | ~220°/с |
| 0.9 | ~310°/с, почти на месте |

Для отладки удобно гонять короткий маршрут на 2–3 секунды.

## Живая муха в окне (Windows, без Docker)

`run_live.py` показывает муху в окне MuJoCo в реальном времени, а управлять ей можно с клавиатуры.
В Docker так не получится: там нет экрана и видеокарты, а программный рендер рисует кадр
около 88 мс. Поэтому этот режим запускается прямо в Windows через [uv](https://docs.astral.sh/uv/).

Подготовка (один раз):

```powershell
# если uv ещё не установлен; после установки откройте новый терминал
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
uv venv --python 3.12          # uv сам скачает Python 3.12
uv pip install -r requirements.txt
```

Запуск:

```powershell
uv run run_live.py
```

| Клавиша / мышь | Действие |
|---|---|
| ↑ | идти |
| ↓ | стоп |
| ← / → | поворот; повторное нажатие делает поворот круче (0.3 → 0.5 → … → 1.0) |
| левая кнопка + тянуть | вращать камеру (она следует за мухой) |
| правая кнопка + тянуть / колесо | сдвинуть / приблизить камеру |
| двойной клик по мухе, затем Ctrl + правая кнопка | толкнуть муху |

Остальные клавиши встроены в сам MuJoCo. Например, буквы переключают отображение
(каркас, коллизионные формы), Tab / Shift+Tab открывают панели настроек.
Если картинка стала странной, просто перезапустите окно.

Чтобы успевать за реальным временем, физика считается грубее, чем в `run_route.py`.
Настройки задаются константами в начале `run_live.py`:

| | `run_route.py` | `run_live.py` |
|---|---|---|
| шаг физики | 0.1 мс | 0.25 мс |
| частота контроллера | 10 000 Гц | 500 Гц |
| noslip-итерации MuJoCo | 5 | 2 |
| скорость на i7-9700F | ~16× медленнее реального времени | **~0.95× реального времени** |

Походка при этом почти та же: за 1 с ходьбы 12.9 мм против 13.1 мм, поворот на 0.3 за 1 с
+105° против +111°. Грубее нельзя: при шаге физики 0.5 мс муха начинает подпрыгивать,
а при контроллере 250 Гц повороты слабеют вдвое. Текущая скорость показана в левом верхнем углу
окна: если она меньше 1.0, муха движется чуть замедленно. Быстрее реального времени симуляция
не идёт, лишнее время она ждёт.

## Как это устроено

`run_route.py`, по шагам:

1. `make_locomotion_fly()` + `FlatGroundWorld` + `Simulation`: муха на плоской арене.
2. `fly.add_tracking_camera(mode="track")`: камера над мухой. Её ориентация фиксирована в мире,
   поэтому на видео поворачивается муха, а не арена.
3. Каждый шаг маршрута превращается в двумерный сигнал `[левая, правая]` (функция
   `descending_signal`). Этот сигнал получает `HybridTurningController`: он задаёт
   амплитуду и направление CPG-осцилляторов своей стороны тела. Контроллер
   возвращает углы суставов и включение адгезии для каждого шага физики (0.1 мс).
4. Кадры рендерятся в память и в конце сохраняются в MP4.

## Версии и окружение

- Python 3.12 (`python:3.12-slim-trixie`, закреплён по digest), flygym **2.1.0**, mujoco **3.9.0**.
  Все зависимости зафиксированы в `requirements.txt` (полный `pip freeze`). Тот же файл
  используется и для живого режима на Windows; там добавляется только `win32-setctime`.
- **dm_control не нужен**: FlyGym 2.x собирает модель через `MjSpec` самого MuJoCo,
  зависимости от dm_control больше нет, поэтому версию для него фиксировать не пришлось.
- Рендеринг: `MUJOCO_GL=egl` через Mesa (программный рендер llvmpipe, GPU не нужен).
  OSMesa тоже проверен и работает с той же скоростью. Если EGL на другой машине не заведётся:
  `docker compose run --rm -e MUJOCO_GL=osmesa -e PYOPENGL_PLATFORM=osmesa sim`.

### Где документация расходится с реальностью

- **Официальный образ `nelyepfl/flygym:v2.1.0` не подошёл как база.** Его Dockerfile начинается
  с `FROM python:3.12-trixie`, но виртуальное окружение внутри создано `uv sync` и работает
  на **Python 3.14.6** (uv скачал свой интерпретатор). Это нарушает требование «Python 3.9–3.12»,
  поэтому образ собран на `python:3.12-slim-trixie` с теми же системными библиотеками. К тому же
  он меньше: в официальном образе есть GPU-бэкенд warp и инструменты разработки.
- FlyGym 2.x требует Python ≥ 3.12, так что из диапазона 3.9–3.12 подходит только 3.12.
- `HybridTurningController` больше не входит в ядро `flygym`. Он лежит в
  `flygym_demo.complex_terrain` (ставится тем же `pip install flygym`). Теперь это не
  gym-окружение, как в 1.x: `controller.step(signal, obs)` только возвращает команды,
  а применять их к симуляции и шагать физику нужно самому.
- Если отрендерить кадр до первого шага физики, получится полностью белое изображение.
  Поэтому сначала вызывается `sim.warmup()`.

## Известные ограничения

- Ходьба «прямо» не идеально прямая: на первых шагах курс уходит примерно на 10° влево,
  и каждый шаг ноги курс колеблется на ±5°. Поэтому сводка в `run.log` усредняет курс
  по последним 0.1 с шага.
- Инерция: амплитуда CPG меняется плавно (около 0.3–0.5 с). Часть поворота досчитывается
  уже в следующем шаге. После `stop` муха ещё проходит около 1 мм и доворачивает на 20–30°.
- Скорость поворота зависит от `strength` нелинейно, её надо подбирать по `run.log`.
- `run_route.py` медленный: около 15× медленнее реального времени, только CPU. GPU-бэкенд warp
  не используется: он ускоряет тысячи мух параллельно, а не одну. Для живого просмотра есть
  `run_live.py`, но его физика чуть грубее, поэтому он не повторит видео из `run_route.py` точь-в-точь.
- Все кадры хранятся в памяти до конца прогона: около 45 МБ на секунду модели.
  Минутный маршрут потребует около 2.7 ГБ RAM в Docker Desktop.
- Только плоская арена, без препятствий и сенсорной обратной связи от среды (зрение, запахи).
